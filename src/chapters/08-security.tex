\chapter{Security considerations}
\label{ch:security}

The platform hosts vulnerable software on purpose, so it has to hold up against the same classes of bug that it teaches. This chapter lists the safeguards, where each secret lives, and the issues that verification left open.

The iframe sandbox allows scripts and keeps the lab's own origin, because the challenges need both. That makes the separate origin a hard requirement for every deployment: if the lab were served under the platform's domain, a reflected XSS payload would run with the platform's origin and could read the Clerk session cookie.

\section{Open issues}
\label{sec:open-issues}

Probes run on 23~September~2026 on the team's development machine, with Docker 29.6.1, found the following gaps. None of them affects grading, but each one weakens a boundary above.

\begin{itemize}[leftmargin=1.4em]
\item From inside the lab container, a DNS lookup of the host name \code{db} fails with \code{ENOTFOUND}, but a TCP connection to the database container's IP address on port 5432 opens.
\item A TCP connection from the lab to the database port published on the host (5433) also opens.
\item The Compose file uses a development password for PostgreSQL, which would make either open path more serious outside a development machine.
\item Flag submissions have no rate limit. The 64-bit flag token makes guessing impractical, but a limit would still cut noise in the attempt log.
\item The lab container has no CPU or memory limit in the Compose file.
\end{itemize}

The planned fix has three parts. Firewall rules on the VM will drop traffic from the lab network to the platform network and to the host. The database port will not be published outside the host, and its password will come from a secret. The Compose file will set resource limits for the lab. After each change the team will run both probes again. Until both probes fail, the lab cannot be described as having no network route to the database.
